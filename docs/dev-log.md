## 2026-09-26 项目启动

### 仓库初始化

- 提交了 README、AGENTS.md、.gitignore 和 requirements.txt（`2b91d47`）。目前依赖只有 `torch`。
- 本机是 Apple M5（24 GB 内存），PyTorch 可以用 MPS。另有一台 RTX 3060 笔记本，可用来跑耗时较长的训练。

### 目标：以理解为主，不追求训练规模

- 仓库以学习为主，不追求复现 GPT-2 的训练结果。
- 模型实现是否正确，不靠训练来验证，而是加载 OpenAI 官方 GPT-2 124M 权重，和参考实现对比 logits。
- 训练只要求跑通流程：小模型跑几百步，loss 正常下降即可。需要长时间训练时，放到 3060 笔记本上跑。
- 因此代码要自动选择设备（`cuda` → `mps` → `cpu`），换机器时不用改代码。
- 放弃的方案：从零预训练 GPT-2 124M。在 M5 和 3060 笔记本上都不现实，原始规模的复现用了 8 张 A100 和约 100 亿 token。

### 学习路线

| 阶段 | 做出什么 | 学习什么 | 完成标准 |
|---|---|---|---|
| 0 | 字符级 bigram 热身：字符编号表与 `encode` / `decode`，一个能训练、能续写文本的小模型 | 词表与 token、Tensor、Embedding、输入与目标右移一位、交叉熵、反向传播、训练循环 | 编码后能解码回原文；loss 下降；能学会 `"abcabc…"` 这类简单重复序列 |
| 1 | Tokenizer：先实现简单 BPE，再实现 GPT-2 的 byte-level BPE | 子词切分、字节到 Unicode 的映射、合并规则、特殊 token | 简单 BPE：encode 后能解码回原文，合并过程符合预期。GPT-2 BPE：加载官方 `encoder.json` / `vocab.bpe` 后，编码结果与 `tiktoken` 的 `gpt2` 编码逐 token 一致，包括 `<\|endoftext\|>` |
| 2 | 模型结构：`wte`/`wpe` → 多头因果自注意力 → Transformer block → 完整模型 | Q/K/V、因果遮罩、多头注意力、MLP（GELU 的 tanh 近似）、Pre-LayerNorm、残差、`ln_f`、`lm_head` 与 `wte` 共享权重 | 各层 tensor 形状正确并有标注；参数量为 124,439,808；改动第 t 个位置之后的 token，前 t 个位置的 logits 不变 |
| 3 | 加载官方 GPT-2 124M 权重 | 参数名映射、Conv1D 权重需要转置、数值误差、与参考实现对照 | CPU float32 下，同一输入的 logits 与参考实现一致（`atol≈1e-4`） |
| 4 | 生成：输入提示词，输出续写 | 自回归生成、temperature、top-k、top-p | greedy 解码与参考实现逐 token 一致；固定随机种子下，采样满足预期性质（如 top-k 之外的 token 概率为 0）；加载权重后能生成通顺的英文 |
| 5 | 小规模训练：数据读取、训练与验证、保存和恢复 checkpoint。训练目标：字符级小 GPT（约 6 层、384 维、上下文 256）在 tiny Shakespeare 上训练，在 Colab 的 L4 上跑即可，与阶段 0 的 bigram（验证 loss 2.49）对比；进阶可选：用阶段 1 的 GPT-2 tokenizer 在 TinyStories 上训练小模型 | AdamW、warmup + cosine 学习率、梯度裁剪、梯度累积、过拟合 | 在相同可见上下文不对应冲突目标的固定小 batch 上过拟合，loss 接近 0；检查训练与验证 loss 的趋势；同一后端、可复现设置下，从 checkpoint 恢复后（含优化器状态、随机数状态及数据迭代位置），与不中断训练的结果在约定容差内一致 |
| 6 | 常规训练加速与 124M 基线。必做：用已知手段逐项加速（bf16 混合精度、`scaled_dot_product_attention`、`torch.compile`、融合版 AdamW、把词表补齐到 50304 等，候选清单见 11-14 的记录），整理成逐步加速表；实现 HellaSwag 评测；在 Colab 上从头预训练 124M 基线（FineWeb-Edu 约 100 亿 token，分段续训）。可选：KV cache、在官方 124M 权重上微调（如 Shakespeare） | 性能分析（先找瓶颈再优化）、性能测量、显存管理、断点续训、下游评测 | 加速：从朴素的 float32 实现开始，每次加一项，记录每步耗时、token/s、MFU 和峰值显存；每项都要证明结果不变，即前若干步的 loss 曲线与上一步在容差内一致，KV cache 开启前后的 greedy 输出完全一致。基线：正式开跑前在每张候选 GPU 上各试跑约 100 步，测出 token/s 和计算单元消耗；跑完后在同一验证集上与官方 124M 对比 loss，HellaSwag 与官方 124M 和 Karpathy 的复现结果对比 |
| 7 | 现代化对比与自己的研究（拓展）。① 2 × 2 对比：GPT-2 结构或现代结构（RoPE、RMSNorm、SwiGLU、GQA、QK-norm），分别配基线训练方法（AdamW + cosine）或现代训练方法（Muon、WSD），小规模各跑一次。② 研究方向 A（暂定）：拆解 GPT-2 结构，先逐项测出每个现代组件的贡献，再尝试自己的改法。③ 研究方向 B（暂定）：训练效率，在常规加速之后用 profiler 找剩下的瓶颈，尝试自己的优化（如自写 Triton 融合算子、分析 MFU 与理论上限的差距）。④ 可选：同样预算下换数据集或调整数据配比。⑤ 最优组合跑一次完整规模 | 消融实验的设计：控制变量、随机种子带来的波动、先小规模试验再放大、公平调参、参数量对齐；Triton | tokenizer、数据顺序、验证集和 token 预算都与基线相同；结构对比要保持参数量一致；只有超出多个随机种子波动范围的差异才算提升。指标：验证 loss、达到基线最终验证 loss 所需的 token 数、HellaSwag、吞吐。效率优化要证明结果不变，并量化它在常规加速之外又快了多少。最终：最优组合在完整规模上与基线对比，主指标是"训练到与基线同等的 loss 所需的总时间和成本" |
| 8 | 保留拓展（可选，阶段 7 之后再定）：后训练——在 124M（自己预训练的或官方的）上做 SFT + DPO，得到一个迷你聊天模型；int8 / 4-bit 量化；大模型规模的工程问题（分布式训练、大规模数据处理、推理部署）。分布式训练需要 AWS 多卡服务器，费用更高，暂缓 | 对话格式与特殊标记、只在回答部分算 loss 的掩码、偏好数据与 DPO loss、量化与混合精度的区别、并行训练方式 | 后训练：模型按问答格式回答，并在回答结束时停下，与后训练前的续写行为对比；其余到时另定 |

### 阶段 0 的初步设计（待正式开始时确认）

- `warmup/bigram.py` 包含以下部分：
  - `CharTokenizer`：字符按排序后的顺序编号。`set` 的遍历顺序每次运行都可能不同，所以要排序。
  - `get_batch(data, block_size, batch_size)`：返回 `x` 和 `y`，形状都是 `(B, T)`，`y` 是 `x` 右移一位。
  - `BigramLanguageModel`：`forward` 始终返回形状为 `(B, T, V)` 的 logits；`generate` 接收整条序列作为输入，这样换成 GPT-2 后几乎不用改。
  - `estimate_loss`：返回 Python float。
  - `main`：训练流程。
- 超参数参考 Karpathy 的 `ng-video-lecture`：`block_size` 8、`batch_size` 32、学习率 1e-2、训练 3000 步。
- `tests/test_bigram.py` 覆盖以下内容：
  - tokenizer 编码后能解码回原文，且编号按字符顺序分配。
  - `get_batch` 的输出形状、右移一位，以及 `data` 长度恰好为 `block_size + 1` 时的起点边界。
  - logits 形状，以及 loss 与 logits 一致。
  - bigram 只看当前 token。
  - `generate` 保留输入的前缀。
  - 在 `"abcabc…"` 上训练后，能确定地续写下去。
- 数据用 tiny Shakespeare（约 1 MB，放在 `data/`，不进版本库），下载命令由用户自己运行。
- 新增 `pytest` 依赖，并在 `pyproject.toml` 里设置 `pythonpath = ["."]`，这样直接运行 `pytest` 也能导入仓库里的模块。
- 预期结果：初始 loss 约为 ln(65) + 0.5 ≈ 4.7（embedding 用 N(0, 1) 随机初始化，所以高于 ln(65)），训练后降到 2.5 左右。

## 2026-11-14 新增阶段 7：现代化改进与对比实验

- **决定**：先完成阶段 0–6 的 GPT-2 基线，再把现代大模型的结构和训练方法逐项加进去，量化每一项的提升，结果要能写进简历。这部分新增为阶段 7。原来的阶段 7（后训练、量化、大规模工程）顺延为阶段 8，此前记录里说的"阶段 7"指的都是现在的阶段 8。
- **对比哪些改动**：
  - 结构：RoPE、RMSNorm、SwiGLU、GQA、QK-norm 等。
  - 训练方法：WSD 学习率（可以在最后加一段退火）、Muon 优化器等。
  - 用户自己的优化：等基线和上面的对比结果出来以后，自己选一个切入点去尝试，具体方向到时再定。
- **怎样比才可信**（已写进阶段 7 的完成标准）：
  - 控制变量：tokenizer、数据顺序、验证集和 token 预算都与基线相同，一次只改一项；如果是几项一起改，要写明。tokenizer 必须保持不变，否则 loss 没法比。
  - 随机波动：小规模实验中，每个配置跑 2–3 个随机种子。只有提升超过种子之间的波动，才算真的有提升。
  - 公平调参：新结构或新优化器的最佳学习率可能和基线不同，每个配置都要简单扫一遍学习率，否则对比不公平。
  - 指标：验证 loss、HellaSwag 和吞吐（token/s）。主指标用"达到基线最终验证 loss 所需的 token 数"，这样提升可以直接说成"少用 X% 的 token"。
- **算力安排**（估算，未实测）：
  - 一次完整的 124M 训练（100 亿 token）约需 75–100 个计算单元，接近一个月的额度。
  - 所以完整规模只跑两次：一次基线，一次最终效果最好的组合。
  - 逐项对比放在小规模上做，例如 124M 只训约 10 亿 token，每次约 8–10 个单元；挑出有效的改动，再放大验证。
  - 小规模具体取多大，等阶段 6 测出实际速度后再定。
- **参考**：Keller Jordan 的 modded-nanogpt。这个项目在 GPT-2 124M 上逐项加入现代改动，按"达到固定验证 loss 需要多少时间"来排名；Muon 优化器最早就出自这里。
- **分布式训练暂缓**：Colab 只有单卡，做不了；AWS 的多卡服务器可以做，但费用更高。这部分放在阶段 8，以后再考虑。
- **数据集：基线不换**。用户确认：基线照常用 FineWeb-Edu，和 Karpathy 的复现结果直接对比；之后在阶段 7 再试换数据集。理由如下：
  - FineWeb-Edu 是 2024 年用现代方法筛选出来的数据（用分类器给每篇文档打质量分），在这个规模上仍然是很好的选择。它总共约 1.3 万亿 token，我们只用 100 亿 token 的子集，原因是算力有限，不是数据不够。
  - 换掉数据集，就没法再和 Karpathy 的复现结果直接对比。
  - 如果想体现"数据"这个方向，可以在阶段 7 把数据当作一个对比项，比如同样的预算下比较 FineWeb 和 FineWeb-Edu，或者加入代码、数学数据，而不是替换主数据集。
  - 如果想和 modded-nanogpt 的公开结果直接对比，就要用它所用的 FineWeb（不是 FineWeb-Edu）和它的验证集。
  - 换数据集做对比时要注意：不同数据集各自的验证 loss 不能直接比较。要么用同一份验证集来算 loss，要么以 HellaSwag 这类与训练数据无关的评测为主。

## 2026-11-14 训练加速：逐项对比，并扩充候选手段

- **决定**：阶段 6 的加速部分也做成逐项对比。除了 bf16、`scaled_dot_product_attention`、`torch.compile` 这些常规手段，再尽量多找其他加速方法，每一项都测量加速前后的差别。已写进阶段 6 的完成标准。
- **和阶段 7 的分工**：
  - 阶段 6 只提高吞吐（每秒处理更多 token），不改变模型学到的东西。所以每一项都要证明结果不变：前若干步的 loss 曲线与上一步在容差内一致。
  - 阶段 7 提高样本效率（每个 token 学到更多），比如 Muon、WSD、新结构，会改变 loss 曲线。
  - 两边分开，提升才能算清楚是从哪来的。会改变训练结果的手段，比如让注意力不跨文档，放到阶段 7。
- **怎么测**：
  - 从朴素的 float32 实现开始，每次加一项，整理成一张逐步加速表，记录每步耗时、token/s、MFU（实际算力占 GPU 峰值算力的比例）和峰值显存。
  - 加每一项之前，先用 `torch.profiler` 找到当前的瓶颈，再决定下一步优化什么。
  - 计时时排除前几步：`torch.compile` 第一次运行要先编译，热身步不能算进去。计时前后要同步 GPU。
  - 正确性在本机验证；速度要在目标 GPU（A100 / G4）上测，因为加速效果和硬件有关。这张表也可以作为选卡的依据。
  - 参考：Karpathy 的 *Let's reproduce GPT-2 (124M)* 就是这样一项项加速的，在 A100 上单步耗时大约降到原来的十分之一。
- **候选加速手段**（还没实测，效果因硬件和规模而不同）：
  - 数值精度：
    - TF32 矩阵乘法（`torch.set_float32_matmul_precision("high")`）。
    - bf16 自动混合精度。bf16 不需要 GradScaler。
    - FP8：只有 H100 和 Blackwell 架构支持，A100 不支持。如果 Colab 的 G4 就是 Google Cloud 的 G4 机型（RTX PRO 6000 Blackwell），就支持 FP8，实际型号要开机确认。124M 的矩阵比较小，FP8 的收益可能有限，需要实测。
  - 编译与算子：
    - `torch.compile`，比较默认模式和 `max-autotune`。
    - `scaled_dot_product_attention`（底层是 FlashAttention）。
    - 融合版 AdamW（`fused=True`）。
    - 对小模型，可以试用 CUDA graphs（`torch.compile` 的 `reduce-overhead` 模式），减少每次启动 GPU 运算的开销。
  - 形状对齐：
    - 词表从 50257 补到 50304（128 的倍数）。补上的编号永远不会出现在数据里，对结果的影响可以忽略。
    - batch 和序列长度取 2 的幂或 64 的倍数。
  - 显存换速度：
    - 交叉熵分块计算或与 `lm_head` 融合计算，不一次性生成整个 `(B, T, V)` 的 logits，能省下大量显存。
    - 省下的显存用来加大 micro batch，从而减少梯度累积的次数。
  - 数据与 CPU 端：
    - 数据提前编码好，存成 uint16 分片并用 memmap 读取。
    - 使用锁页内存和异步拷贝（`pin_memory`、`non_blocking=True`）。
    - 避免每步调用 `.item()` 让 CPU 等 GPU，loss 每 N 步才读一次。
    - 用 GPU 利用率确认 GPU 没有在等数据。

## 2026-11-14 阶段 7 方案与两个研究方向（暂定）

本条细化同日"新增阶段 7"的记录，学习路线表中的阶段 6、7 已同步更新。

## 2026-11-16 训练精度定为 bf16 混合精度，去掉 FP8
